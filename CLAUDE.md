# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Villa Elena is a Laravel 12 / PHP 8.2 / MySQL 8 resort management system for **one single villa property, rented out exclusively as a whole to one guest group at a time** — not a multi-unit hotel. It has four surfaces: an unauthenticated **Public Portal** (browsing/booking), an **Admin Panel**, a **Staff Portal** (frontdesk/walk-ins), and a **Customer Portal** (guest self-service).

**`project.md` at the repo root is the authoritative, actively-maintained design doc** (schema, pricing model, booking rules, route list, deployment, known-issues-fixed history). It is large and versioned (currently v5.3) — read the relevant section before touching booking, pricing, payments, notifications, or deployment code. Don't try to re-derive that history from git log; it's already written down there. When you make a change that this doc describes (schema, pricing, slots, deployment), update `project.md` too — it's treated as living documentation, not a changelog to leave stale.

### Database

Local dev uses `villa_elena_db` on local MySQL (`root`, credentials in `.env` — not reproduced here) with `SESSION_DRIVER=file`, `CACHE_STORE=redis`, `QUEUE_CONNECTION=sync`. Production (Render + Aiven) has no shell access, so a **second `aiven` DB connection** exists in `config/database.php` purely for running one-off artisan commands against production from a dev machine:

```bash
php artisan migrate --force --database=aiven
php artisan migrate:fresh --seed --force --database=aiven   # full prod reset + reseed
```

Migrations use sequential sub-second timestamps to control FK creation order — don't rely on filename dates alone when reordering.

### Redis (cache — local and production, v7.4)

Production caches through Redis since v7.4: a hand-created **Render Key Value** instance (Free, Singapore, internal-only) reached through `REDIS_URL`. Locally it's the Compose container:

```bash
docker compose up -d redis      # starts just the redis service, independent of the app service
```

- **Production runs `CACHE_STORE=failover`, never plain `redis`.** The `failover` store in `config/cache.php` is `['redis', 'database']`: Redis first, MySQL whenever Redis can't answer. With plain `redis`, a Redis outage throws out of `Setting::get()` in `CheckMaintenanceMode` and every public page 500s. Before v7.4 the cache could only fail together with the DB.
- `REDIS_CLIENT=predis` is required everywhere: neither the Docker image nor XAMPP has the `redis` extension. `max_retries`/`backoff_*` in `config/database.php` are phpredis-only. The setting that matters under predis is `REDIS_TIMEOUT` (0.5s, feeding `timeout` and `read_write_timeout`); predis's own default is 5s per command.
- **`Setting::get()` reads every setting as one entry (`Setting::CACHE_KEY`) through `Cache::memo()`**, so a request makes at most one real cache read. Don't return to per-key entries or drop the memo: while Redis is down, every real cache read pays `REDIS_TIMEOUT`. Invalidation lives in the model's `saved`/`deleted` events, so the seeder's `updateOrCreate()` clears it too.
- **Locks that guard correctness use `Cache::store('database')`, never the default store.** Under failover a Redis blip puts two requests' locks in two different stores, and both win. A Redis lock also throws at `get()`, past the point failover can catch it. The PayMongo checkout lock is pinned this way.
- `CacheFailedOver` is logged as a `WARNING` (`AppServiceProvider`). To spot an outage, search Render's log for `fell back to the next store`.

`REDIS_HOST` in `.env` is `127.0.0.1` (correct for `php artisan serve` reaching Redis's published port) — the Dockerized `app` service below overrides this to `redis` (the Compose service name) since `127.0.0.1` inside that container means the container itself, not the sibling Redis one.

### Full app in Docker (parity testing, NEW)

`docker compose up --watch` runs the app in the **same `Dockerfile`/image Render deploys** (PHP 8.2-fpm-alpine + nginx + supervisord) — use it to check whether a change behaves the same in that stack before pushing, rather than only finding out after a deploy. `php artisan serve` is unaffected and still the default for day-to-day work.

- Reaches local MySQL via `host.docker.internal`, authenticating as a scoped `villa_docker`@`%` MySQL user (not `root` — see `project.md` §15.7 for the one-time `CREATE USER`/`GRANT` setup) — the container doesn't present as `localhost` to MySQL, so `root`'s `localhost`-only grant doesn't match.
- Bind-mounts `storage/` (needs to persist uploads/sessions/cache across restarts) and `public/build/` (the built JS/CSS). **`public/build` must stay a bind mount, never a watch `sync` rule:** it is listed in `.dockerignore`, and Compose Watch applies `.dockerignore` to its sync rules, so a rule for it copies nothing and says nothing — that is how a correct `admin.js` fix stayed invisible on `localhost:8000` (which is the container, not `php artisan serve`). JS/CSS changes need `npm run build` on the host, not a rebuild; the mount hides the image's own build, so a missing host `public/build/` 500s every page. `.env` is read once at container creation (`env_file`) — restart to apply, no `--build`. The full what-needs-what table is in `project.md` §15.7. Everything else you'd actually edit (`app/`, `resources/`, `routes/`, `config/`, `database/`) is synced in via Compose Watch (`develop.watch` in `docker-compose.yml`) rather than live bind-mounted — a plain bind mount of the whole repo works but is multiple seconds slower per request on Windows (every `vendor/` file read crosses the Windows↔WSL2 boundary). `composer.json`/`package.json`/`Dockerfile`/`docker/` changes trigger an automatic rebuild instead of a sync. Every sync entry has `initial_sync: true`, so starting watch first pushes the current host files in; without it the container served the code baked in at the last build until each file was touched again. It only works under `--watch`: a container started by plain `up` or a Docker Desktop restart still runs the image's old code.
- **Never bind-mount or sync `bootstrap/cache/`** into this container. It holds Laravel's compiled package-manifest cache; the host's copy reflects a full `composer install` (dev packages included), and mounting it over the image's clean `--no-dev` build throws `Class "...ServiceProvider" not found` at container start. Same underlying reason `.dockerignore` (excludes `vendor/`, `node_modules/`, `.env`) has to exist at all — without it, a local `docker build` (unlike Render's, which always builds from a fresh clone) copies local dev-only artifacts straight into the image and produces a build that doesn't actually match what Render runs.

## Architecture

### Routing & roles

Four route files, each gated by role middleware (`RoleMiddleware`, aliased as `role` in `bootstrap/app.php`):

| File | Prefix | Middleware | Purpose |
|---|---|---|---|
| `routes/web.php` | `/` | none | Public portal, auth, PayMongo payment routes |
| `routes/admin.php` | `/admin/` | `auth, role:admin` | Admin panel |
| `routes/staff.php` | `/staff/` | `auth, role:staff,admin` | Staff portal |
| `routes/customer.php` | `/my/` | `auth, role:customer` | Customer portal |

Controllers mirror this under `app/Http/Controllers/{Admin,Staff,Customer,Portal}/`, plus `app/Http/Controllers/Auth/AuthController.php` for shared auth. Post-login redirect is role-based: admin → `/admin/dashboard`, staff → `/staff/frontdesk`, customer → `/my/`.

### The single-villa model

`properties.type` is an enum of just `villa` / `room`. There is exactly **one** `type=villa` row — the only bookable listing; the `type=room` rows are informational only (status badges, images, housekeeping) and are never independently bookable or shown in customer-facing listings. Don't reintroduce per-room booking.

**Don't hardcode a room count, and don't select the villa by name.** This file used to say "6 rooms"; the local dev database has **3**, and production could not be checked from here (the `aiven` connection fails TLS — see `project.md` v7.39). The count is not load-bearing anywhere in the code, and neither is the name: every lookup is `Property::where('type', 'villa')`, never a name match. The seeder writes "Villa Elena (Whole Villa)" while the local row is called "Villa Elena", so a name-based lookup would already be broken.

### Booking slots & pricing (current model, v7.59)

- Every booking is one fixed slot from `App\Models\Booking::SLOTS` — `day` (8:00 AM–5:00 PM, 9 hrs), `night` (7:00 PM–6:00 AM next day, 11 hrs), `stay22` (7:00 PM–5:00 PM next day, 22 hrs), or `day22` (8:00 AM–6:00 AM next day, 22 hrs, added v7.59). There is **no free-choice time input anywhere** in booking creation.
- **There are two 22-hour slots, and "the 22-hour slot" below means either (v7.59).** `stay22` and `day22` are both `window_required`, share one rate, and are told apart by name: "22 Hours (7PM)" / "22 Hours (8AM)". **Never test `=== 'stay22'`** — ask `Booking::slotRequiresWindow()` / `windowedSlotKeys()`, or the slot definition's `rate` tag. A `=== 'stay22'` in `Property::priceColumnsFor()` would have sold `day22` at the Day/Night rate, half price. `rate` is a tag (`'22h'`), not a column name, because the definitions are sent to the guest page as JSON.
- **One 22-hour variant per date, and their windows must not overlap.** `day22` overlaps the same date's Day, Night and `stay22`, **and the previous date's `stay22`** (which runs to 5PM). `CalendarController::slotWindowProblem()` refuses a second variant on a date and a window that overlaps another window's stay — without that, booking one leaves the other date offering nothing while its Night stays hidden. That refusal is what lets `slotsOfferedOn()` and the five JS pickers keep returning the first matching window.
- **Three questions, three methods — do not substitute one for another.** `SLOTS` = the definitions (always all of them, so `slotDateTimes()`/`slotKey()`/the calendar can read existing bookings). `Booking::bookableSlotKeys($property)` = what has a **price**. **`Booking::slotsOfferedOn($date, $property)` = what is offered on a given date, and that is what every form, grid, dropdown, validator and public page must ask.** Never hardcode `in:day,night` and never use a date-free list where a date is available.
- **The 22-hour slots are not sold every day (v7.48).** The owner nominates check-in dates in **`slot_windows`** (Admin → Calendar → "22-Hour Date"), and **on a nominated date it is the only slot offered** — Day and Night are hidden there. Everything else stays Day/Night. One row = one offered stay: `check_in_date` is a single date, and the span is derived from `slotDateTimes()`, never stored. It is the *opposite* of `availability_blocks` (which closes a date), though it mirrors that model's shape and its check-in-date matching for the same reason.
- **A window on an unpriced slot deliberately has no effect.** Exclusivity hides Day/Night, so if `stay22` were also unpriced the date would offer *nothing* — a dead date. So a window only takes effect once the slot is priced; otherwise the date falls back to Day/Night. `addSlotWindow()` refuses up front and says to set the rate first.
- **Offering and conflict are separate concerns — keep them separate.** `hasConflict()` and `slotAvailabilityMap()` evaluate **all** slots regardless of windows, because a 22-hour booking must still mark Night and the next day's Day as taken. Only the *offering* surfaces filter by window. Conflating them reopens double-booking.
- **A block, a 22-hour date and a booking are three records about one date, and they must agree (v7.57).** `Booking::blockSpan($checkIn, $checkOut)` is the single definition of which dates a stay claims for the block question: its check-in date, plus any later date it is still in at or after that date's first slot. So a block closes Day and Night on its own date, leaves the previous **Night** open (it ends 6AM), and closes the previous **22 Hours** (it runs to 5PM). `hasConflict()` (via `blockOn()`), the staff grid and `blockedSlotMap()` all read it — never write a second block test, and never pass a raw check-out date to `AvailabilityBlock::coveringRange()`. `addSlotWindow()` **refuses** a date that is blocked, or that has any live booking on it or inside the stay (even a non-overlapping Day booking; only a same-slot booking on that date is exempt); `deleteSlotWindow()` refuses while `SlotWindow::holdingBooking()` finds one. Don't bring back a "confirm to continue" there: the old one fired on every date, so the one real warning was indistinguishable. Blocking over a 22-hour date stays **allowed** (the block wins). The admin calendar shows one sign per date: the window bar is hidden once it is booked or its own date is blocked, and relabelled "Not bookable while … is blocked" when the block is on the next day. Calendar drag-move checks the offering rule in `moveOfferingProblem()`, because `reserveSlot()` only tests collisions.
- **Blocked dates reach the guest calendars through `Booking::blockedSlotMap()`, not `slotAvailabilityMap()`** — the latter is `slot => booking_id` for the live "freed" update, and a block has no booking id. The guest label is "Not open" (two short words that may wrap); "Not available" and "Closed" were both measured to clip in a phone-width cell. No block reason is ever sent to a guest.
- **`Property::quoteFor()` is the one fail-closed backstop — `abort(422)` for a slot that is unpriced *or* not offered on that date, never a ₱0 quote.** So Day/Night are refused **on** a 22-hour date, and `stay22` is refused everywhere else. A NULL price reaching arithmetic is how `POST /book/{room}` once created a real ₱0 slot-holding booking (`base_price = 0.00` on room rows; see `PortalController::assertBookableListing()`). `isSlotPriced()` requires non-null **and** > 0; a blank admin field writes NULL, never 0. Being this strict is safe because **no caller ever re-quotes an existing booking** — all seven price a booking about to be made or moved — so opening a window can't break editing a booking already on that date.
- **Slot validation is `App\Rules\SlotOfferedOnDate`, not an `in:` list**, because the allowed set depends on the submitted check-in date. All seven validators use it; it takes the date field's name (`checkin` vs `check_in_date`), and deliberately adds no error when the date is missing — that field's own rule reports it.
- **The five pickers duplicate the offering rule in JS** (villa page pills + radios, landing hero, walk-in, admin create, customer reschedule), fed by `Booking::slotWindowDates()`. The rule is **window first and exclusive, otherwise the non-windowed slots** — keep the JS and `slotsOfferedOn()` identical, or a form will offer a slot the server refuses. `slotWindowDates()` ships only priced slots' dates so the two can't drift on that axis.
- ⚠️ **`stay22` is the first slot that overlaps another slot.** A Friday 22-hour booking holds Friday `night` **and Saturday `day`**; conversely a Saturday `day` booking closes Friday's `stay22`. `hasConflict()` and `slotAvailabilityMap()` handle this with no special cases because both are **datetime-overlap** tests (the map already walks `check_in_date - 1`). **Never replace either with a "same slot key?" comparison** — it looks equivalent and silently permits a double-booking. Anything new that reasons about slot occupancy must overlap datetimes too; three places got this wrong by matching on check-in time alone (`slotKey()` below, and the occupancy and outcome code of the old recommendations engine — `OccupancyCalendar::loadBookings()` is its overlap-based successor).
- `Booking::slotDateTimes($slot, $checkInDate)` is the single source of truth converting a slot + date into check-in/check-out `Carbon`s — every booking-creating controller (public portal, customer reschedule, staff walk-in, admin create) must go through it rather than parsing raw time fields.
- **The reverse lookup is two methods and they are not interchangeable (v7.46).** `Booking::slotKey()` answers *"what was this booked as"* — it reads the stored **`bookings.slot`** column, falling back to an exact time match — and is for labels and form pre-fill. `Booking::exactSlotKey()` answers *"do the stored times still define a slot exactly"* (check-in **and** check-out **and** day-span) and is for anything computing a **duration**. Matching on check-in time alone was only ever safe while each slot had a unique one; `night` and `stay22` both start at `19:00`. Using `slotKey()` for a duration re-creates the original bug: it deliberately still answers `night` for a stay `extendStay()` lengthened, so a calendar drag-move would rewrite a 22-hour booking as 11 hours, or erase an extension. `Admin\CalendarController::moveBooking()` is the one duration caller and uses `exactSlotKey()`.
- **`bookings.slot` is model-maintained and not fillable**, like `slot_hold`, but its rule is the opposite: `slot_hold` is recomputed from scratch on every save, while `slot` is **preserved** when the times no longer match any slot. That preservation is the whole point — it's what keeps an `extendStay()`-lengthened booking labelled `night` when its times no longer say so. **The slot is decided at check-in (v7.59): the hook re-reads it from the times only when `check_in_date` or `check_in_time` is dirty, or the column is empty.** "Preserve when nothing matches" was not enough, because an extension can land exactly on another slot's times (Night extended to 5PM = `stay22`, Day extended to 6AM = `day22`) and the hook runs on every save. Don't loosen that condition, and don't add a path that changes a booking's slot while keeping its check-in date and time — the hook cannot see it. Both columns go through `hasOptionalColumn()` so they tolerate code deployed ahead of the migration.
- Slot labels come from the `name` / `times` fields on the `SLOTS` entry. **Never build one with `ucfirst($slotKey)`** (renders "Stay22") or a `$slot === 'day' ? 'Day' : 'Night'` ternary (reports "Night" for every non-Day slot). Seven display sites had one of those.
- `Booking::hasConflict()` does a plain check-in/out **datetime** overlap against the single villa's existing bookings — there is **no separate cleaning-buffer parameter**; the gap baked into the `day`/`night` slots (5PM→7PM, 6AM→8AM, both 2 hrs) already serves that purpose.
- **`Booking::reserveSlot($propertyId, $checkIn, $checkOut, $callback, $excludeBookingId)` is the only sanctioned way to create or move a booking** — `hasConflict()` alone is a bug. It is a SELECT, so calling it and then writing leaves a window in which two concurrent requests both see the slot free and both take it. That is not hypothetical: `VE-4C7INQOG` and `VE-YHLBMLUU` are two live production bookings on the same 2026-09-15 Day slot, `created_at` identical to the second, both paid (v7.0). `reserveSlot()` wraps the check and the write in one transaction under `lockForUpdate()` **on the `properties` row** — a real row that always exists, so serialization is deterministic instead of depending on InnoDB gap-lock behaviour over a range that may match nothing. All seven paths go through it: portal submit, admin create, admin extend stay, admin calendar drag-move, staff walk-in, customer reschedule. Keep the callback DB-only — mail, Pusher broadcasts and notifications belong after the commit.
- **`bookings.slot_hold` + its UNIQUE index is the database-level backstop**, and it is model-maintained: never mass-assign or hand-write it. `Booking::computeSlotHold()` returns `"{property_id}:{check_in_date}:{check_in_time}"` while the booking holds its slot and **NULL** when it doesn't (`cancelled`, `no_show`, or soft-deleted) — MySQL allows repeated NULLs in a unique index, which is exactly why a cancelled booking's slot frees up while two *live* bookings on one slot remain impossible to store. Its exclusion list must stay identical to `hasConflict()`'s; if they drift, the index will reject a booking the availability grid advertises as open. A `saving` hook recomputes it, and a `deleted` hook nulls it (`SoftDeletes::runSoftDelete()` bypasses `save()`, so the `saving` hook never fires on a soft delete). **It is a weaker backstop since v7.47:** the key includes `check_in_time`, and `19:00` is the check-in for both `night` and `stay22` — so it still catches those two colliding on one date (correctly, they do conflict) but **cannot** catch `stay22`-vs-next-day's-`day`, which is a different date and time. `reserveSlot()`'s row lock is the only guard there. Likewise `day` and `day22` share `08:00` (caught), while `day22`-vs-`night` and `day22`-vs-`stay22` are caught only by the lock (v7.59).
- **`reserveSlot()` formally cancels overlapping expired holds inside its lock**, via `Booking::releaseAsExpiredHold()` (shared with `AutoCheckInOutBookings::cancelStalePendingBookings()`). This is required, not decorative: `hasConflict()` *ignores* a `pending` booking past `booking_hold_minutes`, but that row still carries a `slot_hold`, so without the release the index would refuse an INSERT for a slot the grid shows as free. It also means correctness no longer depends on the external cron pinger actually running.
- `Booking::confirmOnFirstPayment()` re-checks availability before promoting a booking to `confirmed`. A guest whose hold expired can still have a live PayMongo checkout link; paying through it used to confirm them onto a slot someone else had since taken. The payment is always recorded (never throw money away) — the booking is left `pending` and admins are notified, which is also the state the stale sweeper won't touch, since it skips anything with `amount_paid > 0`.
- The one deliberate exception is `Admin\BookingController::extendStay()`, which extends an already-checked-in guest's stay and is still free-choice on the new checkout time.
- Pricing is a flat package rate from `Property::getPackagePrice(Carbon $checkin, ?string $slot = null)` (NOT the older `getPriceForDate()`, which is date-only and still used only by `PricingRule`/legacy paths): Mon–Thu and Sun-after-6PM → `base_price` (₱4,000 regular); Fri/Sat/Sun-before-6PM → `weekend_price` (₱6,000 peak). An active `pricing_rules` row for the date overrides both. **`$slot` picks the column pair** (`Property::priceColumnsFor()`): `day`/`night` share `base_price`/`weekend_price`, while `stay22` and `day22` share their own `base_price_22h`/`weekend_price_22h` (the slot's `rate` tag) because a 22-hour stay consumes two slots' worth of villa time. Price follows the check-in time, so on a Sunday `day22` (8AM) is peak and `stay22` (7PM) is regular. **A percentage `pricing_rules` override applies on top of the normal price for that date and slot (v7.58)** — weekday or weekend, Day/Night or 22 hours. Until v7.57 it multiplied the slot's *weekday* base, so "+10%" on a Saturday charged ₱4,400 instead of ₱6,000; don't put it back on `$base`. A `fixed` rule is still absolute.
- **`Property::quoteFor($checkin, $slot)` — not `getPackagePrice()` — is what booking code calls.** It is to price what `slotDateTimes()` is to time: the single source of truth. It wraps `getPackagePrice()` and subtracts any matching seasonal promo, returning `['base', 'discount', 'total', 'promo']`. Every pricing path goes through it (portal preview/form/submit, staff walk-in + availability grid, admin create, customer reschedule); `getPackagePrice()` is only for a bare list price. Never recompute a discount at a call site — and never reimplement pricing in JavaScript, which is exactly how the walk-in form drifted (its client-side copy couldn't see `pricing_rules` or promos, and its overpayment guard measured against that wrong number; it now fetches `GET /staff/walkin/quote`).

### Seasonal promos (v6.0)

`discounts` was dead schema until v6.0 — `bookings.discount_amount` was hardcoded `0` everywhere. It now backs **automatic** promos: the guest types no code; a promo applies when the booking's **check-in date** is inside its window and `applies_to` matches the slot. Admin-only CRUD at `/admin/promotions` (`Admin\PromotionController`); staff can't create promos but walk-ins get them automatically. Rules that must survive edits:

- Discount comes off `base_amount` **only**, never extras — matches `recalculateBookingTotals()`'s `base + extras - discount`.
- Promos never stack; on overlap the **largest peso discount** wins (not the largest percentage — they differ once a `fixed` promo is involved), tie-broken by highest `id`.
- **A promo has two independent eligibility axes, and they are different questions (v7.49).** *When / which slot* is the date window + `applies_to`. *Who* is `discounts.guest_scope` — `all` (the default, and what every promo was before v7.49) or `returning`, with `min_completed_bookings` as the threshold. `Discount::isValidOn($checkIn, $slot, $guest)` tests both; `isEligibleGuest($guest)` is the *who* axis alone. The owner's regular-customer discount lives here rather than in a new table because it is the same object with one more test — reusing the window, the slot match, `used_count`, `bookings.discount_id` and `bestFor()`'s competition.
- **`User::completedStayCount()` counts `checked_out` bookings and nothing else.** `pending`/`confirmed` would let anyone become a "regular" by creating bookings they never pay for; `checked_in` is a stay not yet finished. It's memoised per instance, and the count query only runs when a candidate promo is actually `returning`-scoped.
- **`quoteFor($checkin, $slot, $guest)` fails closed on a null guest, and that default is load-bearing.** A `returning` promo does not apply without a guest, so a call site that forgets the argument charges the **list price**. The opposite default would show a low preview and charge more at submit — the exact failure the single pricing choke point exists to prevent. A bigger bill can never be a pleasant surprise; an unexpected discount can. Three sites pass `null` deliberately and say so in a comment: `pricePreview()` (unauthenticated route), `buildSlotGrid()` (a date×slot table with no guest in it), `OccupancyCalendar::quote()` (a recommendation is about a date, not a person — and it keeps the `date|slot` cache key valid). Both AJAX quote endpoints accept `user_id` and re-quote when the selection changes; a walk-in only passes it for an *existing* guest, since a brand-new one cannot be returning.
- **Loyalty promos compete, they never stack** — same `bestFor()` sort. A regular during a seasonal promo gets the bigger of the two. Confirmed with the owner. Stacking would need a `booking_discounts` pivot, because `bookings.discount_id` is one FK, `discount_amount` one number and `used_count` one counter; the whole promo accounting rests on that one-discount invariant.
- **`publicActive($viewer)` drops a `returning` promo the viewer can't get, and that creates a second bug you must keep fixed.** Advertising "20% OFF" to someone who'll be charged full price is the failure; but staying silent makes the chatbot say "There are NO promos running right now" to a regular who isn't signed in, and under v7.20 **a denial is a claim too**. When the viewer **is** eligible, the promo is listed normally and the prompt states plainly that it isn't available to every guest, so Elena can't relay it as a general offer.
- **`Discount::returningTeaserFor(?User)` returns three states, and must never be collapsed back into a bool (v7.50).** It answers what to tell a viewer who *isn't* getting a loyalty promo: `null` (nothing to say — none live, or they already qualify), `guest` (not signed in → "Stayed with us before?" + sign-in), `short` (signed in but below the threshold → "You're N stays away", **no sign-in CTA**). The previous bool knew the viewer was excluded but not *why*, so a signed-in guest three stays short was told to sign in. `need` is the **lowest unmet** threshold, not the highest — that's the next one actually reachable; quoting a higher one advertises a tier they may never hit. Stating `need`/`have` is fine under v7.20 (it's our own data); the discount's size still is not. The landing page and the chatbot prompt both read this one method, and the chatbot's `short` branch tells Elena the guest **is** signed in so she can't repeat the bad advice.
- **The announcement audience must use the same eligibility rule as the price (v7.50).** `PromotionController::broadcastToCustomers()` blasted every active customer with no `guest_scope` filter — correct in v6.0, wrong the moment v7.49 added the *who* axis, and it notified 4 ineligible guests out of 8 on a real promo. That's the worst shape this bug can take: a notification promising a discount the guest cannot have, with nothing to see when they tap it. `announcementAudience()` applies `User::scopeWithCompletedStays($min)` — a `whereHas(..., '>=', $min)` sub-select, so it stays one query and `chunkById()` still never holds the table in memory. **`User::COMPLETED_STAY_STATUS` is the single definition** shared by `completedStayCount()` and that scope; two places answering "what is a completed stay" differently is exactly how this broke. The title/body also say *why* the guest got it, or a targeted discount reads as a general one and gets passed to someone who can't use it.
- **`NotificationHelper::notifyGuest(..., broadcast: false)` is for bulk blasts only.** `NotificationCreated` is `ShouldBroadcast` with `QUEUE_CONNECTION=sync`, so each notification is a **blocking** Pusher HTTP call inside the request — 8 guests took ~12s, which is why a promo save looked hung and got clicked twice (two promos, two blasts to the same guests; `notified_at` can't help, it guards one row). The trade-off is explicit: no realtime toast for an announcement, the bell catches it next page load. **Never pass it for payment, booking or issue-report notifications**, where realtime is the whole point.
- **Creating a promo is guarded against an accidental double submit**, because a duplicate blast cannot be taken back (deleting the promo leaves the notifications). `Discount::duplicateProblem()` follows the `Payment::manualEntryProblem()` split — an identical promo within 10 minutes is *suspicious*, not *wrong*, so it blocks and asks ("Create it anyway") rather than refusing. Disable-on-submit is an affordance only; the server guard is the barrier, same reasoning as `policies_accepted`. `notify()` also checks `notified_at` now — it used to call `broadcastToCustomers()` directly, and the Announce button only disappears once the response renders, so two fast clicks both went through.
- Deposits compute off the **discounted** total, and so do the walk-in overpayment guard and payment-type detection.
- `used_count` moves with reschedules (decrement old promo, increment new). Deleting a promo is `nullOnDelete()` on `bookings.discount_id`; `discount_amount` stays, so historical totals never change.
- `guest_scope`/`min_completed_bookings` are rendered through `$promo->guest_scope_label` ("Returning guests (2+ stays)") and `->guest_scope_note` (the guest-facing sentence), for the same reason `slot_label` exists: three views show this, and a drifted copy states a rule the code doesn't enforce. An `all`-scope promo normalises its threshold back to 1 on save, so a later edit to `returning` can't inherit a number nobody looked at.
- `applies_to` is `ENUM('all','day','night','stay22','day22')` — keep it in step with `Booking::SLOTS` (`stay22` was added in v7.47, `day22` in v7.59; MySQL drops a column default on a bare `MODIFY`, so restate `DEFAULT 'all'`). The promo form deliberately offers **every** slot including unpriced ones: a promo may be prepared before a slot launches, and `applies_to` is not a claim about what's bookable today. `all` needs no migration to cover a new slot — `isValidOn()` only compares when `applies_to !== 'all'`.
- **A promo announcement is stored text, so it goes stale the moment the promo changes (v7.51).** Nobody is overcharged — `quoteFor()` reads the live row — but the guest is left relying on terms that no longer exist. Two rules follow. **(1) Guest-facing text never says "no end date":** use `$promo->guest_window_phrase` ("until further notice", "for stays until Nov 05, 2026"), never `window_label`, which is admin wording. An undated promo can be switched off at any time, so "no end date" was a promise the system could not keep; the chatbot prompt uses the same accessor and is told an undated promo is not permanent. **(2) A change to an announced promo is never silent:** `PromotionController::notifyPromoChange($old, $current)` runs from `update()`, `toggle()` and `destroy()` and sends *Promo Update* / *Promo Ended* / *Promo Is Back*. It fires only for `Discount::MATERIAL_FIELDS` (`type`, `value`, the two dates, `applies_to`, `guest_scope`, `min_completed_bookings`) — **`label` and `description` are deliberately excluded, which is what keeps the "a typo fix doesn't re-blast" rule intact; don't add them.** The audience is the one under the **old** terms (they are who was told — raise the threshold 5→8 and the guest with 6 stays must hear it), except *Is Back*, which uses the current ones. Nothing is sent for a never-announced promo or one already past its expiry. Any new way of changing or ending a promo must call it.
- Announcements are **in-app only, one-time**, guarded by `notified_at` (edits to the name or description don't re-blast; material changes send an update, see above). Do not add email here — Brevo's free-tier quota is shared with 2FA, booking confirmations and password resets.
- The landing-page banner (`is_public`) is the primary channel, because guests who aren't logged in have no `user_id` and `NotificationHelper` cannot reach them at all.
- **`Discount::publicActive()` (the banner) deliberately includes promos whose window hasn't started yet**, while `isValidOn()` (the pricing) does not. A September promo must be advertised in August — that's when it can still influence a booking — but it must not discount an August stay. Don't "fix" the banner query to match the pricing query; only `expiry_date` bounds it.
- Dates are guarded in `PromotionController::validated()`: `expiry_date` can never be in the past, and `start_date` can't be moved into the past — but an already-running promo may **keep** its existing past `start_date` through an edit, so renaming a live promo doesn't force a date change.
- `Portal\ChatbotController` **is** promo-aware: it prices through `quoteFor()` and always injects a `CURRENT PROMOS` block built from the same `Discount::publicActive($viewer)` the landing banner uses — both pass `Auth::user()`, so the banner, the prompt and the charged price can't disagree about who qualifies. The block is unconditional — when there are no promos it says so explicitly, because an empty section invites the model to invent one. Keep that "there are NO promos" branch if you touch it.
- **The chatbot prompt is grounded, and the grounding rule is a principle, not a list (v7.20).** Every factual claim must come from the prompt's data sections, which are declared to be the complete extent of Elena's knowledge — and the rule **covers denials**, since "no, we don't have that" is a claim too. Don't refactor this back into a list of banned topics: the previous prompt banned inventing prices, amenities and promos, and the model then invented staffing, a WiFi password (`Wifi` is in `amenities`, so it assumed the credentials existed too) and a pet policy. `"Only answer about Villa Elena Resort topics"` does **not** cover this — it is a topic filter, and "is there a girl there?" is on-topic. Keep the named no-data list (staffing hardest), keep the hand-off naming the real `resort_phone`, and keep the guest transcript fenced between BEGIN/END markers as neither instruction nor fact. **Never add `check_in_time`/`check_out_time` (14:00/12:00) to this prompt** — per-night leftovers that contradict the two fixed slots.
- **`GeminiService::ask()` takes `$temperature`, defaulting to `0.7`** so moderation/insights/forecast/briefing are unchanged. The chatbot sends `0.0` for intent extraction (strict JSON) and `0.3` for Elena's reply. Probing the chatbot in a loop hits Groq's **tokens-per-minute** limit (two calls per message) and every reply becomes the apology string — that's the limiter, not a regression; space calls ~25s apart.
- `bookings:auto-checkinout` (`AutoCheckInOutBookings` console command) drives automatic status transitions off the stored `check_in_time`/`check_out_time` — it doesn't need to know about slots at all, just the literal stored datetimes.

### Disk-aware image storage

`config/filesystems.php`'s `public` disk switches to the `cloudinary` driver automatically when `CLOUDINARY_URL` is set (production), local disk otherwise (dev) — no controller code branches on this. Views must use the disk-aware accessors (`$image->url`, `$property->primaryImage->url`, `User::profile_image_url`) rather than hardcoding `asset('storage/'.$path)`, which only works for the local disk.

**Never call `Storage::disk('public')->url()` on an image field — go through `App\Helpers\MediaUrlHelper::resolve()` (v7.2), which is what all three accessors (`PropertyImage`, `User`, `Package`) now use.** On the Cloudinary driver `->url()` is not string-building like every other disk; the adapter's `getUrl()` is literally `adminApi()->asset($id)->offsetGet('secure_url')` — **one live Admin API call per image, per render**. Cloudinary's free tier allows 500 Admin API operations *per hour*, and the villa gallery alone is 6–8 images per page load, so ordinary browsing exhausts the quota and then **every image on the site disappears** until the next hour, with `Rate Limit Exceeded. Limit of 500 api operations reached.` in the log. That is what the old try/catch was quietly swallowing. No API call is needed: a delivery URL is `https://res.cloudinary.com/{cloud}/image/upload/v1/{public_id}` and the SDK builds it locally, so `MediaUrlHelper` uses zero quota.

- **`MediaUrlHelper::prepareResource()` must stay an exact mirror of `CloudinaryStorageAdapter::prepareResource()`** — that method produced the `public_id` at upload time, so any drift means a 404 for every image. Two easy-to-miss details: the extension is **stripped** from the public ID (re-appended for image/video delivery, but not for `raw`, which was stored without it), and the resource type comes from `FinfoMimeTypeDetector::detectMimeTypeFromPath()`, which is extension-based and touches no filesystem (it must not — in production the file exists only on Cloudinary).
- **Don't resolve `app(Cloudinary::class)`** — the package's singleton reads `filesystems.disks.cloudinary`, but this project's disk is named `public`, so it builds a client with a null cloud name. `MediaUrlHelper` constructs its own from `config('filesystems.disks.public.url')`.
- Uploads and deletes are unaffected: they go through the Upload API (`uploadApi()->upload()` / `destroy()`), which is not the 500/hr Admin API quota.
- Still make sure local `.env` has no stray `CLOUDINARY_URL` (see `project.md` v5.3) — with one set, local dev builds Cloudinary URLs instead of `/storage` ones.

### Admin dashboard live KPIs (v7.9)

Pending Bookings, Total Bookings, Total Guests, Revenue Today, Revenue This Month, and the Revenue Overview / Booking Sources charts update by **refetching**, never by arithmetic on the page. `App\Services\DashboardStats::kpis()` is the single source (render and `GET /admin/dashboard/stats`, uncached, refunds excluded, formatted server-side). `Booking` and `Payment` model hooks call `DashboardStats::touch()`, which fires one empty `stats.changed` per request from `app()->terminating()`. **Don't reintroduce `+1`/`−1` handlers or per-controller dispatches:** that's how Pending stuck at 1 — only `Admin\BookingController::updateStatus()` ever sent the decrement, so confirmation-by-payment, front-desk check-in, the sweeper and guest cancels never did — and how refunds got *added* to Revenue Today. A new booking-status or payment path needs nothing extra; the model hook already covers it. Don't add a live value back into the controller's `admin_dashboard_stats` cache — a second, 60s-stale copy is what let a refresh contradict the live number. The charts redraw from the `admin:dashboard-stats` DOM event, only when the data differs. The `Booking` hook watches `status` **and** `source` (the donut). The `User` hook fires only on create, `role` change or delete — keep it that narrow, since users are saved on every login. The admin `payment.received` toast must branch on `is_refund`: refunds ride the same event, and without it a refund is announced as incoming money.

### Staff Availability live grid (v7.10)

`/staff/availability` refreshes its grid by fetching server-rendered HTML from `GET /staff/availability/grid` (the same `staff/_availability_grid.blade.php` partial and `buildSlotGrid()`), triggered by an empty `availability.changed` on `staff-frontdesk` plus a 60s fallback. **Never reimplement slot availability in JS** — the whole point is that the live grid and a reload go through one `hasConflict()`. The signal comes from `Booking` hooks (create, delete, restore, or a change to `status`/`property_id`/check-in/out date or time) and `AvailabilityBlock` save/delete, via `Booking::touchAvailability()`. Any "tell open pages to refetch" broadcast goes through `App\Services\BroadcastOnce::dispatch($key, …)` — once per request, from `terminating`, never throws (it runs inside the PayMongo webhook) — with its own key. The staff realtime partial loads **after** page scripts, so a staff page reaches the channel via `window.rtStaffChannel` or the `staff:realtime-ready` event, not by assuming it exists. Expired holds and passed slots have no event; only the 60s refetch catches them.

### Recommendations — prescriptive analytics (v7.58)

`/admin/prescriptive` is **five IF–THEN rules**, not a model. It was rebuilt in v7.58 because the expected-revenue version rested on an assumed price elasticity nobody could defend and, on real data, produced one card. `project.md` v7.58 has the measurements.

- **Every occupancy rule reads three counts from `OccupancyCalendar::summarise()`:** *booked so far* (booked ÷ offered slots), *usual* (the same weekdays over the last 180 days, Day and Night only), and *predicted occupancy* = the larger of the two. A stretch is one week's weekdays (Mon–Thu) or weekend (Fri–Sun).
- **The rules** (`app/Services/Prescriptive/Advisors/`): quiet stretch → promo; busy stretch **or** a public holiday (the holiday dates only) → percentage pricing rule; no maintenance scheduled → block the quietest free gap; back-to-back bookings → turnover-clean task; balance due before check-in → in-app reminder.
- **The percentages and thresholds are the owner's policy** — six `prescriptive_*` settings (Admin → Settings → Booking Rules → Recommendation Rules). Don't bring back a formula that computes a discount, a peso "projected gain", or a "confidence" label: those are what made the page impossible to explain, and their columns are dropped.
- **A stretch's identity is its week and kind, never its first date.** A fingerprint built from `today + 2` changes every day, so a dismissed card would come back tomorrow.
- **"Usual" must not count the 22-hour slot**, and "taken" stays a datetime-overlap test (`Booking::blockSpan()` for blocks). Counting overlaps as 22-hour demand once gave it the highest fill rate in the table with three real bookings.
- **The engine writes only `recommendations` rows.** Promo, pricing rule, block, housekeeping task and reminder are created in `PrescriptiveController::apply()` when a person presses the button — claimed under `lockForUpdate()`, then logged twice (`applied_recommendation` + the manual path's own action name). A new action type needs a `staleReason()` case, a creation method, an entry in `Recommendation::ACTIONS`, and both log names.
- **The turnover card is not the automatic checkout task** that v7.11 removed: nothing is sent until the admin presses Send task.
- **A pricing rule has no admin screen**, so the page's own "Turn off rate" (`turnOffRate()`) is the only way to undo one without the database.

### Cancellation & refund policy (v7.52)

**All payments are non-refundable when the guest cancels — deposit and full payment alike, at any time, with no grace period.** That is the owner's policy. The refund question is **who** cancelled, never **when**; the old 100/50/0 tiers (`calculateRefundPercentage()` / `calculateRefundAmount()`) are deleted, so don't reintroduce a time-based rule.

- **`Booking::CANCELLATION_POLICY` is the one guest-facing sentence.** Terms §9, the booking form, checkout, the booking-detail cancel panel, admin Settings and the chatbot prompt all print it. Never type the policy into a view — five separate copies is how three of them came to disagree, and how the chatbot promised "free cancellation up to 48 hours".
- **The refund machinery stays, because three refunds are not guest cancellations:** the resort cancels (full refund, Terms §9), a double charge / overpayment, and a payment that arrives after the slot was taken. Don't remove Send Money, `refund_destinations`, `refund_transfers` or `PaymentController::refund()` in the name of "no refunds".
- **Guest cancel creates no refund row** and leaves `amount_paid` on the booking. A paid booking needs `accept_no_refund`, validated server-side — the checkbox's `required` is an affordance only. Unpaid bookings cancel freely.
- **Admin cancel asks `cancel_initiator` (`guest` | `resort`), with no default, and refuses a paid booking without one.** It cannot be inferred from the booking, and a wrong guess moves money the wrong way. `resort` → `Booking::resortCancellationRefund()` (everything paid) as a `pending` refund.
- **Rescheduling to a cheaper slot does not refund the difference.** `Customer\BookingController::update()` stops *before* `reserveSlot()`, states the difference and requires `accept_no_refund`. The leftover excess must not reach `flagOverpayment()` unexplained — its alert says "charged twice, return the excess" — so `overpayment_notified_at` is stamped first and the reschedule notification says "not a double charge". Any new path that lowers a paid booking's total needs the same two steps.
- **`cancellation_hours` no longer exists** and the cancellation policy is not a setting. `deposit_percentage` defaults to **50** everywhere.
- `RESCHEDULE_CUTOFF_DAYS = 7` now exists so the resort can resell a freed slot, not to match a refund tier.

### Housekeeping & issue reports (v7.11)
Check-in **no longer creates a `checkout_clean` task**. The owner decided the admin sends tasks (`/admin/housekeeping`), so don't reintroduce an automatic one. Guests with a `checked_in` booking (`Booking::canReportIssues()`) and staff file `issue_reports`, which go to the staff frontdesk **and** the admins at once, never admin-first: the admin portal isn't always open. Status changes for tasks and reports go through `HasWorkStatus::markStarted/markCompleted/markCancelled()`. Those are conditional UPDATEs that return `false` when another click got there first; the frontdesk is one shared monitor. Staff realtime sends go through `App\Services\FrontdeskBroadcast::send()`, which never throws.

**Issue reports are live on all three surfaces (v7.14).** The signal comes from the model: `IssueReport`'s `created` hook and `HasWorkStatus::transition()` → `workStatusChanged()` (the UPDATE is query-builder, so there is no Eloquent `updated` event). They send an empty `issues.changed` on `staff-frontdesk` and `admin-dashboard`, plus `DashboardStats::touch()` for the `open_reports` sidebar badge. Pages refetch server-rendered partials (`staff.frontdesk.housekeeping`, `admin.housekeeping.live`, `customer.bookings.issues.index`) and never rebuild the list in JS. A guest-report status change also sends the guest an in-app notification plus `issue.updated` on their private `notifications.{id}` channel. That event is the customer layout's toast and is never emailed.

**Blade:** never use the one-line `@php($x = …)` in a view that has a `@php … @endphp` block later on. The compiler pairs them and swallows everything in between (`unexpected token "endforeach"`). Use `@php $x = …; @endphp`.

### UI conventions (v7.53)

- **Describe a booking to a guest by slot and time, never by `num_nights`.** It is written as `max(1, …)`, so a Day slot reads "1 night". Use `$booking->slot_name`, `->check_in_time_label`, `->check_out_time_label`, `->stay_hours`; the times come from the stored columns so an `extendStay()` booking shows its real checkout.
- **`max_advance_days` is enforced for guests only**, through `Booking::latestBookableDate()` / `advanceLimitRule()` / `advanceLimitMessage()` on the portal booking and customer reschedule validators and as `max` on their date inputs. Staff and admin are not limited. Don't add a field to Admin → Settings that nothing reads — five such fields were removed.
- **Admin `topbar-right` is for page actions only.** Logout and the search button live in `layouts/admin.blade.php`; a page that re-adds either gets two.
- **No native `confirm()` or `alert()` in any view.** Use `<form data-confirm="…" data-confirm-label="…">` or `await confirmDialog('…')` from `partials/confirm_dialog.blade.php` (a `<dialog>`, deliberately not a Bootstrap modal, so it sits above the pages' own modals). It is included by the admin, customer and staff layouts. The button is red by default because most prompts are deletions; a prompt that destroys nothing (check-in, check-out) passes `data-confirm-tone="neutral"` / `{ tone: 'neutral' }`. **Put a guest's name in the `data-confirm` attribute, never in an inline handler**: an `onclick` is parsed as JavaScript after the HTML parser has already undone the escaping.
- **Admin tables stack on a phone (v7.54).** Below 640px a table inside `.table-card` (or a `table.audit-table`) shows each row as labelled blocks instead of scrolling sideways. The labels are the column headings, copied onto each cell as `data-label` by the script in `layouts/admin.blade.php`, so a new table needs a real `<thead>` and nothing else. A page that sets its own `min-width` on the table must not out-rank `.main-content .table-card table.is-stacked`.
- **A password rule is never typed into a view or a placeholder (v7.54).** `App\Support\PasswordPolicy` holds both the rule (`rule()`, which is what `Password::defaults()` returns: 8+ characters, a letter, a number, a symbol) and its wording (`requirements()`). A new-password field gets `@include('partials.password_rules', ['for' => 'fieldId'])` under it, which prints the checklist and ticks it live; change the rule and the wording in that class together, and keep each `pattern` identical to what Laravel's `Password` rule tests, or the checklist will approve a password the server refuses. A show/hide button is `<button type="button" data-pw-toggle="inputId" aria-label="Show password">` (inside `.pw-field` when there is no `.input-group`); `partials/password_ui` handles both and is included by the auth, admin, staff and customer layouts. Give every password input `autocomplete="current-password"` or `"new-password"`.
- This is one villa: say "the villa", not "properties".
- **Actions are `<button>`, navigation is `<a>` — never a `<div onclick>`**, and a `<label>` gets `for` pointing at its control's `id`. The focus ring and the `prefers-reduced-motion` rule are global in `base.css`; don't add `outline: none` without a replacement.
- **Colours, fonts and the primary button come from `base.css` tokens (v7.54), never a hex or a font name in a view.** `var(--font-display)` / `var(--font-body)` (Playfair Display / DM Sans, loaded by `partials/fonts.blade.php`); `var(--btn-primary)` with `var(--btn-primary-hover)`; `var(--border-strong)` for a form field's edge. **Gold text on a light surface is `--gold-text`, not `--gold`** (2.8:1), and a button never hovers to gold with white text. Text is 12px or larger. The one place a hex literal is right is a Chart.js colour: a canvas cannot read a CSS variable. Reach for the helper classes in `base.css` (`.field-label`, `.field-hint`, `.note-text`, `.text-red`, `.mt-12` …) before writing a `style=""`.

### Mail / broadcast failure handling

Outbound mail (registration, 2FA send/resend, verification, forgot-password, walk-in guest creation) and Pusher broadcasts (`NotificationHelper::create()`'s `event(new NotificationCreated(...))`) are wrapped in try/catch + `Log::error()` rather than left to bubble up — a transport hiccup must degrade gracefully (request still succeeds) rather than 500 the whole flow. Follow this pattern for any new mail/broadcast call site, especially inside a DB transaction (a failed non-critical email must not roll back the primary action). Several other `event(new BookingUpdated/FrontdeskUpdated/PropertyAvailabilityChanged(...))` call sites in bookings/calendar/frontdesk still have the old unprotected shape — treat them the same way if you touch them.

Notification `link` values must be generated as relative URLs (`route($name, $params, false)`) — an absolute URL bakes in whatever `APP_URL`/tunnel host was active at creation time and goes dead if that changes.

### Rate limiting (v7.8)

Every public route that sends mail, calls the AI or checks a secret uses a **named limiter** from `AppServiceProvider::configureRateLimiting()`; the full table is in `project.md` v7.8.

- **Per-minute limits alone are not enough.** Brevo's free tier (300/day) is shared by 2FA codes, password resets and booking confirmations, and the Groq budget is shared by the chatbot, review moderation and admin reports. Anything that sends mail or calls the AI gets an hourly or daily cap too.
- **Over the limit, send the guest back to the form with a message, never to an error page.** Put it where that page reads it: `error` flash on auth pages, the form's **named error bag** on the profile page, `contact_error` on the contact form, JSON `{ok:false, reply}` for the chatbot.
- Every `Limit` inside one limiter needs its own key prefix (`m:`/`h:`/`d:`); a shared key means a shared counter.
- **Never throttle `/webhooks/paymongo*`**: a 429 is a failed delivery, and PayMongo disables the webhook.
- Login is locked on **failed** attempts per account (`AuthController::login()`), not on requests per IP. A 2FA code is cancelled after 5 wrong guesses. Across codes, each account is also capped at 6 codes per hour, 12 per day and 15 wrong guesses per hour: any path that issues a code must call `twoFactorIssueProblem()` before `issueTwoFactorCode()`, because a correct-password login issues a fresh code with five fresh guesses.

- **A verification link only completes in a session signed in as that account** (`AuthController::verifyEmail()`); signed out, it goes through login and `afterLoginRedirect()` brings the guest back. The click proves the inbox, not the password — without this, an account registered on a stranger's address gets verified by the stranger. For the same reason **never overwrite an unverified account with a newer sign-up**. A completed password reset sets `email_verified_at`, and `users:prune-unverified` removes sign-ups unverified after 48 hours (see `project.md` for what it must never delete).
- Slow work in `register()` and `sendResetLink()` (mail, admin notification) runs in `defer()`, not inline and not `app()->terminating()`: inline, response time reveals whether the address is registered.

### Non-obvious column/enum names

These have caused real bugs before (see `project.md` §13 for the full list) — don't assume Laravel-convention defaults:

- `settings` table: `setting_key` / `setting_value` (not `key`/`value`)
- `notifications.is_read` (integer 0/1, not `read_at`); `type` is almost always `in_app` in practice even though other enum values exist
- `housekeeping_tasks.task_type` enum: `checkout_clean` (not `checkout_cleaning`/`checkout`), `daily_clean`, `maintenance`, `inspection`
- `payments.status` must be set explicitly to `success` at every creation site — the DB column defaults to `pending` and nothing auto-promotes it
- `users.status` is cast/compared as integer (`isActive()` → `(int)$this->status === 1`)
- `properties.amenities` is a JSON array; the *available* amenity options list is admin-managed via `Setting::get('property_amenities')`, not hardcoded

### AI & payments integration

- **The AI report pages must not call Groq on a page view.** `/admin/insights` and `/admin/forecast` read the last generated text out of `App\Services\AiReportStore` (`Cache::store('database')`, stored forever, no TTL); only `POST /admin/{insights,forecast}/refresh` calls Groq, and `ThrottlesAiRefresh` caps that at one per minute per admin. `/admin/prescriptive` has always worked this way (it reads what `prescriptive:generate` wrote). Don't move an `ask()` call back into an `index()`, and don't make a Refresh button an `<a href>` to the page's own GET — that was the original bug, and it makes the button a no-op while every idle visit spends a request. The store is pinned to the `database` cache store on purpose (production's Redis is the non-persistent free plan) and deliberately avoids the `settings` table (`Setting::get()` loads every setting as one blob on every public page).
- **The AI provider is a `.env` switch: `AI_PROVIDER=groq|gemini`** (`config('services.ai.provider')`, default `groq`, so an environment that never sets it — production today — is unchanged). Switch it, then `php artisan config:clear`. **Never test another provider by rewriting `GeminiService.php`** — that is how the Groq implementation was overwritten, and the replacement shipped three bugs at once (v7.5): a URL of `"https://googleapis.com{$apiKey}"` that glued the key onto the hostname (DNS failure on every call, and cURL wrote most of the key into `laravel.log`); retired `gemini-2.5-flash`, which **404s while `GET /models` still lists it** (test a model with a real `generateContent`, never the listing); and `responseMimeType: application/json` forced on every call, which wraps plain text — moderation got `"CLEAN"` with the quotes and would have sent every review to the manual queue, insights got a JSON array. Gemini rules that came out of measuring `gemini-3.6-flash`: key in the `x-goog-api-key` header, never the URL; no JSON mode (the chatbot intent step parses 3/3 without it); **`thinkingLevel: minimal` by default** (`GEMINI_THINKING_LEVEL` overrides, `omit` sends none), because thinking tokens count against `maxOutputTokens` — at the briefing's 500 cap the default spent 476 tokens thinking and returned a 100-char fragment; `thinkingBudget: 0` 400s with a generic "invalid argument" that doesn't name the field, so the retry-without-thinkingConfig fires on any 400. Keys are read per call from config, not in the constructor: a typed `string` property assigned `config('services.groq.key')` throws `TypeError` when that key is unset, before the switch is even consulted. `ConnectionException`s are logged by class only — their message contains the request URL.
- AI (chatbot, review moderation, insights/forecast): Groq or Gemini via `App\Services\GeminiService` (name is legacy — it calls whichever `AI_PROVIDER` selects) and `ReviewModerationService`. **The model is not hardcoded** — it comes from `config("services.groq.model")` (`GROQ_MODEL`, default `openai/gpt-oss-20b`), because Groq retires models on a rolling basis and `llama-3.1-8b-instant` was already decommissioned out from under this app. Check the live list with `GET https://api.groq.com/openai/v1/models` before assuming a model id still resolves. Groq's current chat models are all *reasoning* models, and hidden reasoning is billed against `max_tokens` — left unconstrained the reply comes back truncated — so `GeminiService` sends `reasoning_effort`. **Do not hardcode that value either:** the families disagree (`openai/gpt-oss-*` wants `low|medium|high`, `qwen/*` wants `none|default`, `groq/compound*` rejects the parameter outright), so `groqReasoningEffort()` derives it from the model id and a 400 mentioning `reasoning_effort` is retried once without it. `GROQ_REASONING_EFFORT` overrides; `omit` skips it. Reviews auto-publish via a keyword pre-filter + LLM classification pass; anything flagged, or if the AI call fails (fail-open), falls back to the admin approval queue. **`ask()` returns `?string` — `NULL` on failure or empty content, never the provider's error text as the reply** (v7.5). It used to return `'API Error: '.$status.' — '.$body`, which every caller then rendered: guests saw Groq's raw JSON (model id, org id, quota figures) in the chat bubble, and insights/forecast printed it as their report. Details go to the log; each surface picks its own user-facing wording on NULL, and the chatbot also returns `ok => false` so the front end keeps that apology out of the conversation `history` it sends back. Don't reintroduce a sentinel string — a guard every caller must remember to string-match is not a guard.
- Payments: PayMongo (`app/Services/PayMongoService.php` — the old unreferenced duplicate under `app/Http/Services/` was deleted in v5.7). **Online checkout requests `payment_method_types => ['qrph']` only** — QR Ph covers GCash, Maya and bank apps in one activation, so the per-wallet integrations aren't enabled. `payments.payment_method` is `ENUM('qrph','cash')`; keep any new payment-writing code inside that set (`PaymentController::recordPaymongoPayment()` normalises unexpected gateway values rather than letting the INSERT fail).
- QR Ph is **asynchronous** — the guest scans a QR, often on a different device, so the success callback may never fire. `POST /webhooks/paymongo` (CSRF-exempt) is therefore the primary recording path, not a fallback; both it and the success callback go through the same `recordPaymongoPayment()`, made idempotent by `reference_number`. Don't add a second payment-recording code path.
- **Two different duplicate-payment problems exist; don't confuse them (v7.1).** *Duplicate recording* is one payment written twice — guarded by `recordPaymongoPayment()`'s `reference_number` check **plus** the `payments (booking_id, reference_number)` UNIQUE index, since that check alone is a read-then-write and the webhook lands exactly while the success callback is running. A `UniqueConstraintViolationException` there is the normal outcome of that race and is caught and treated as "already recorded", not an error. Manual payments keep `reference_number` NULL, and MySQL doesn't enforce a unique index when any key part is NULL, so cash entries are unaffected. *Duplicate charging* is two genuinely different payments (`pay_xxx` differs), which idempotency cannot catch by definition — that's `createCheckout()`'s job.
- **`createCheckout()` must never create a second checkout session for a booking that already has a usable one.** It holds `Cache::lock("paymongo-checkout:{id}")` (not a DB transaction — there's an HTTP call inside), re-reads the booking, refuses when `balance_due <= 0`, and calls `reusableCheckout()`, which redirects to the existing session's `checkout_url` when it's still open, or to `payment.success` when it turns out already paid (which records it). Deposit is `min($depositAmount, $balance_due)` — **the deposit is a percentage of `total_amount`, not of the balance**, so without that cap a stale checkout page on a fully-paid booking creates a live charge. `showPaymentPage()`'s `balance_due` guard is not enough; it only covers the GET.
- **A PayMongo checkout session never expires by itself, so a cancelled booking stays payable until we close it (v7.60).** Only the QR inside it has a clock (30 minutes), and reopening the link draws a new one. `Booking`'s `saved` hook calls `closeCheckoutSession()` whenever `status` becomes `cancelled` — in the model because there are three cancel paths and the one that forgets leaves a live QR. It runs in `DB::afterCommit()`, never throws, and **keeps `paymongo_session_id` when PayMongo refuses** (400 = paid or being paid): the success callback needs that id to record the payment. `AutoCheckInOutBookings::closeLingeringCheckoutSessions()` retries for 24 hours.
- **A payment can still land on a cancelled booking, and `confirmOnFirstPayment()` does not cover it** — it only acts on `pending`, and the sweeper cancels an unpaid hold within a minute. `Booking::reinstateAfterLatePayment()` brings the booking back as `confirmed` only when the **system** cancelled it, check-in is still ahead, the slot is still offered, and `reserveSlot()` finds it free; otherwise it stays cancelled and admins get "Payment on a cancelled booking". Three rules: it runs **after** the payment transaction commits (a deadlock in a nested `reserveSlot()` rolls the payment back with it); **never call it from `reconcileBooking()`** (a later duplicate delivery would silently confirm a booking the admin was told to refund); and the not-reinstated guest gets no confirmation email and no "confirmed" wording.
- **An overpayment is invisible unless something looks for it.** `recalculateFinancials()` clamps `balance_due` with `max(0, …)`, so a booking paid twice looks identical to one paid correctly (`paid`, ₱0 due). `Booking::flagOverpayment()` runs at the end of that method — the one choke point every payment path already calls — and notifies admins **once**, guarded by `bookings.overpayment_notified_at` (cleared when the excess is refunded, so a later episode alerts again). It never auto-refunds; that's a human decision.
- **All three manual payment paths go through `Payment::manualEntryProblem()`** (admin booking page, admin payments page, staff front desk). It blocks an amount above `balance_due` outright, and blocks a same-amount/same-method/same-day repeat unless `confirm_duplicate` is ticked — those are different questions: over the balance is *wrong*, a look-alike is only *suspicious* (a guest really can pay ₱1,000 twice in a day). Three copies of this would drift, and a drifted guard is no guard on the path left behind. Refunds skip it.
- **QR Ph refunds live on a different API host** — `https://refunds-api.paymongo.com/v1/refunds`, not `https://api.paymongo.com/v1/refunds`. The main host returns `400 "Refunds are not allowed for payments with source type qrph."` for every QR Ph payment, which through v5.8 this project wrongly recorded as proof that QR Ph refunds are impossible. They are not (see `project.md` v5.9 for the re-verification). Verified constraints on the correct host: **full amounts only** (`422 partial_refund_not_allowed`), 30-day window, requires available wallet balance, and the refund is a **transfer link the guest must claim within 3 days** — not a reversal. There is **no GET endpoint and no documented webhook**, so refund progress can't be tracked in code.
- **The refund API is nonetheless the wrong tool here, and was rejected.** Full-only collided head-on with the old 50% cancellation tier and with reschedule price differences (both gone since v7.52, see *Cancellation & refund policy*), and it still collides with a manual partial refund or an overpayment — none of which is a full refund of a payment. **The chosen direction is Send Money / Disbursements** (`POST https://api.paymongo.com/v2/batch_transfers`), a plain outbound transfer from the merchant Wallet: arbitrary amounts, InstaPay real-time, `callback_url` for status, ₱10/transfer, and — decisively — **simulator destination accounts** (`999999990001` → `succeeded`, `999999990003` → `account_not_found`, …) so every failure path can be rehearsed on test keys. Note `/v2/wallets` needs a **trailing slash** (301 otherwise).
- **Send Money is built (v5.9 Phase 4)** — `RefundTransferService` + `POST /admin/payments/{payment}/send`, recording every attempt in `refund_transfers`. Verified against real money on 2026-08-23 (two ₱1 InstaPay transfers, one `succeeded`, one `AC06`-rejected). Rules that came out of that and must not be undone: **a `201` does not mean the money arrived** (accepted as `pending`, rejected by the receiving institution 2s later), so only `succeeded` may close a refund; call PayMongo **outside** any `DB::transaction()` (money moving inside a transaction that later rolls back leaves no record of it); claim the refund in a locked transaction *before* the API call so a double-click cannot send twice; and **keep the manual `markRefundPaidOut()` flow** — it is the only path for cash and for failed transfers.
- **PayMongo Send Money facts that are nowhere in the docs** — all learned empirically, so don't "correct" them from the docs: `GET /v2/wallets/` **omits** `balance`/`account`/`limits` unless requested, and `fields` is a **repeated** param (`?fields=balance&fields=account`), not comma-separated — reading the balance without it silently yields `0` and looks like an empty wallet. **Write that query string literally into the URL**: passing `['fields' => ['balance','account']]` to Laravel's `Http::get()` serialises via `http_build_query()` to `fields[0]=…&fields[1]=…`, which PayMongo ignores, producing the same silent empty-wallet result (this shipped once and threw *"The PayMongo wallet has no source account"* on a funded, activated wallet). The fee is **₱10 per transfer, charged only on success** (`fee` reverts to `0` on failure, so retries are free) — but that **reversal is asynchronous**: reading `fee` at the instant a transfer flips to `failed` still returns `1000`, which is exactly when the inline poll reads it, so `syncStatus()` forces `fee = 0` for any non-`succeeded` status instead of trusting the API there. Live rejections use **ISO 20022 codes** (`AC06`/`BlockedAccount`, `metadata.sub_code` `RJCT` vs `ACTC`) — the `account_not_found`/`account_not_active` strings in `transfer-test-cases` are **simulator-only** and never appear live. `provider_reference_number` echoes our own `reference_number` on creation and only becomes the bank's trace after settlement, so re-read it. **The test-mode wallet returns `{"data":[]}`** — HTTP 200, no error, no wallet — so the simulator is unreachable and every failure path must be reasoned about rather than rehearsed. That also means **Send Money cannot work on test keys at all**; `RefundTransferService::send()` checks `PayMongoService::isTestMode()` up front and refuses with a message naming the real reason, rather than letting it surface as "Could not reach the PayMongo wallet" (which reads like a network fault). Checkout is unaffected: `qrph` checkout sessions are created and active on test keys. Webhook secrets are **per-mode** — swapping to test keys means swapping `PAYMONGO_WEBHOOK_SECRET` to the test one and registering the webhook again in test mode, or every delivery fails signature verification.
- **Refund recipient details cannot be derived from the QR Ph payment** — it carries none of `destination_account.{number,name,bic}`; `billing` is just what `createCheckoutSession()` sent, echoed back. Hence `refund_destinations` (asked of the guest) and `refund_transfers` (an immutable snapshot per attempt) are separate tables. There is **no account-name-inquiry endpoint**, so a wrong name only surfaces as a runtime rejection. Detect mobile-number-style accounts by **BIC, never by institution name** (`RefundDestination::MOBILE_WALLET_BICS`) — `MAYA BANK, INC` (`MYDBPHM2XXX`) is a real bank and a different institution from the `Maya Philippines, Inc.` wallet (`PAPHPHM1XXX`), and a `str_contains($name, 'maya')` test wrongly forces bank customers to enter a mobile number.
- 🟢 **GCash `AC06` is intermittent, and no payload field prevents it.** The API reaches GCash fine (`tr_9bc989fa…` landed). The proof it is nondeterministic: `tr_2125e015…` failed while being **identical in every merchant-controlled field** to two dashboard transfers that succeeded hours earlier — same source, destination, name, amount, rail, `purpose`, `description`, reference shape. Same payload, both outcomes; `AC06 BlockedAccount` on an account that accepted money 69 seconds later. **So retry — `RefundTransferService::send()` loops up to `MAX_ATTEMPTS` (3)**, one `refund_transfers` row and a fresh `reference_number` per attempt, stopping early on success or a non-retryable code (`RefundTransfer::RETRYABLE_ERROR_CODES` = `AC06`/`AB08`/`9910`/`91`; account-detail codes like `AC01`/`BE01` are excluded, and `status = 'error'` is never retried since the request shape is what broke). The admin is notified **once**, after the last attempt, with the attempt count — suppress in-loop failure notices with `syncStatus(..., announceFailure: false)`, but never suppress success, which is what closes the refund. **`MAX_ATTEMPTS = 3` is a guess, not a measurement** — the real success rate is unknown; measure it with `php artisan paymongo:probe-transfer` (sends one controlled transfer, every field settable, touches no DB row) before tuning it. **Four confident diagnoses here were already wrong**, each from a small sample where one variable happened to correlate: "GCash blocks the wallet", "Send Money needs more than ₱5" (falsified by our own ₱1 and ₱2 to Maya), "the dashboard sends something we can't see" (`GET /v2/transfers` shows both payloads in full — read it first), and "the `purpose` field decides". **Before concluding that a field matters, send the same payload twice.** `MINIMUM_AMOUNT` is `0.00`: do not reintroduce a minimum without a transfer that proves one. When a transfer fails, do not trust the error code's implied cause.
- `RefundDestination::NO_AUTO_TRANSFER_BICS` and `PESONET_ONLY_BICS` are both **empty** by design; the mechanisms remain for an institution that genuinely needs them. If you ever repopulate `PESONET_ONLY_BICS`, remember PESONet is batch-cleared on banking days (11am/2pm/5pm), so never poll it inline — `AutoCheckInOutBookings::syncPendingTransfers()` is the backstop that closes those when the callback doesn't arrive. Never delete the manual `markRefundPaidOut()` path either way: it is the only route for cash and for failed transfers.
- **Live testing found five bugs that the fake-backed test suite structurally could not.** Each sat in a seam the fakes stubbed over: a fake `PayMongoService` hid that `Http::get(['fields' => [...]])` serialises to `fields[0]=…` and silently returns a wallet with no `account`; direct method assertions hid that the payments *list* only ever offered the manual button; `compileString()` reports a view as valid because `{{ payment_status }}` inside a CSS comment **is** valid PHP, and only rendering catches the runtime "Undefined constant". Verify seams with a real render, a real read-only API call, or a real click — fakes prove logic and nothing else.
- **`PaymentController::webhook()` must never return a non-2xx status.** PayMongo auto-disables a webhook that repeatedly answers 4xx/5xx, it does not recover on its own, and nothing in the app can detect the disabled state — every payment after it simply stops being recorded. So the endpoint is a `try/catch (\Throwable)` shell around `handleWebhookEvent()`, which **returns arrays and never calls `response()`**; keep that split, and don't reintroduce a `401` for a bad signature or let an exception escape. The accepted cost is that PayMongo won't retry a failed event, so the `unmatched_booking` and `processing_error` paths notify admins instead. `transferCallback()` wraps each `syncStatus()` individually for the same reason.
- **When a webhook goes dead, check the registered URL before the secret.** In v6.9 production was registered at the bare origin (`https://villa-elena.onrender.com`, no `/webhooks/paymongo`); `POST /` is 405 from the router, so **nothing reaches the controller and nothing appears in the app log** — the empty log is the symptom, not evidence that deliveries stopped. `php artisan paymongo:webhooks` lists id/status/URL/events for the current key's mode, flags any wrong path, repairs it (`--webhook=… --url=…`), revives disabled ones (`--enable=all`) and parks dead ones (`--disable=tunnels`). Note the listing is **per-mode**: a test key sees only test-mode webhooks.
- **The dev machine's ngrok webhook shares the test-mode account with production, so it receives every test-mode event too** — and returns 502 whenever the tunnel isn't running, accruing the same failures that disabled production. Its ngrok domain is *reserved and static*, so a changing URL is not the issue; an absent tunnel is. `status` is per webhook, not per account, so this can't take production down — it costs the next local test session, silently. Park it with `--disable=tunnels` between sessions. **That probe treats only no-connection or 5xx as dead, never 4xx**: a 4xx means the host answered and rejected the request, which is a code bug to fix, not a registration to remove — the first cut used `>= 400` and would have disabled production, which was answering `401` from the pre-fix code.
- **`php artisan paymongo:tunnel` watches the ngrok endpoint and enables/disables that webhook to match**; `paymongo:webhooks --disable=tunnels` is the manual equivalent (nothing schedules either — `routes/console.php` has no entry). It probes **the registered URL end to end**, never the ngrok agent API: a healthy agent forwarding to a dead port still returns 502, which is the state this project was actually found in, so "a tunnel exists" is not the same question as "the endpoint answers". It refuses any webhook whose host isn't ngrok (`NGROK_HOSTS`) and refuses live keys — without that guard a mistyped `--webhook` would repoint production at ngrok *and* disable it on every exit. Exit-disable is best-effort: `pcntl` doesn't exist on Windows, `sapi_windows_set_ctrl_handler` catches Ctrl+C, and nothing catches `taskkill /F` or a closed terminal (measured — it leaves the hook enabled). That gap is the status quo, not a regression; the next run reconciles.
- **Webhook secrets are per-mode.** The `Paymongo-Signature` header's `te=` slot is signed with the *test* webhook's `whsk_…` and `li=` with the *live* one — different registrations, different secrets. `verifyWebhook()` tries `PAYMONGO_WEBHOOK_SECRET_TEST` then the generic `PAYMONGO_WEBHOOK_SECRET` for `te=`, and `_LIVE` then generic for `li=`. Setting both lets a test-mode and a live-mode webhook share one URL — which this deployment wants, since it runs test keys on the production host. Don't collapse this back to one secret compared against both slots.
- **The guest's payment pages update themselves, and `GET /pay/{booking}/status` — not Pusher — is the authority (v7.7).** QR Ph is asynchronous, so `payment.success` is routinely reached before any money has settled and the checkout page is routinely left open after it has; both poll `payment.status` (backoff 4s→10s→30s, stop at 20 min, paused while the tab is hidden) through the shared `resources/views/payment/_status_watcher.blade.php`. `PaymentReceived` also broadcasts on `PrivateChannel('booking-payment.{id}')`, but the page **never reads an amount out of the event** — it just polls immediately, so a lost, delayed or duplicated broadcast costs nothing and a `is_refund` event is ignored. Don't invert this: Pusher-only breaks silently whenever the websocket does, while displaying money, and `BROADCAST_CONNECTION=log` is the `.env.example` default. `status()` deliberately has **no `balance_due <= 0` guard** (the opposite of `showPaymentPage()`) — the moment the balance hits zero is the answer the page exists to get. The `event()` call added to `recordPaymongoPayment()` is wrapped in `try/catch (\Throwable)` because the webhook runs through it and must never return non-2xx, and because the payment is already recorded by that line. It sits **before** the confirmation email, not after: at the end it landed ~5s late (SMTP) and the 4s poll always beat it. The watcher also **must not stop on the first read that shows the payment** — `amount_paid` is written before `confirmOnFirstPayment()`, so that read can still say `pending`; it re-polls every 3s (max 4) until the status settles, and a Pusher push re-polls even after polling has stopped. Both were found in a real browser, not by the DOM-stub test. Guest-facing payment status text lives in `Booking::paymentProgressDisplay()` so the first render and the polled JSON can't drift; it is **not** `payment_status_label`, which is about the refund stage.
- `bootstrap/app.php` exempts `webhooks/paymongo` from CSRF. Without it the route inherits the `web` group and returns 419 to every real delivery. `bootstrap/app.php` is synced into the Docker container as a **single file** in `docker-compose.yml` — never sync the whole `bootstrap/` directory, since `bootstrap/cache/` breaks container start.
- The first successful payment confirms a booking, via `Booking::confirmOnFirstPayment()` — call it after `recalculateFinancials()` in any new payment-recording path. `recalculateFinancials()` never touches `status`, and `AutoCheckInOutBookings::cancelStalePendingBookings()` cancels stale `pending` bookings, so a payment path that skips it will get paid bookings auto-cancelled.
- Render payment enums through `Payment::$method_label` / `$type_label` (or the `methodLabelFor()` / `typeLabelFor()` statics), never raw `ucfirst(str_replace(...))`. Sort payment lists by `payment_date` **plus `id`** — `payment_date` is date-only, so same-day payments tie and order randomly.
- Report export: `barryvdh/laravel-dompdf` + `maatwebsite/excel`, wired into `Admin\ReportController` (`GET /admin/reports/export/{pdf,excel}`). Both share the same `buildReportData()` the on-screen report uses. Excel export classes live in `app/Exports/` (`ReportExport` is a `WithMultipleSheets` wrapper around per-sheet classes). The PDF view (`admin/reports/pdf.blade.php`) is plain-table HTML — dompdf's CSS support doesn't cover flexbox/grid, unlike the rest of the admin panel's views.

### Frontend build

Vite multi-entry build — one JS/CSS pair per portal section (`admin`, `portal`, `auth`, `staff`, `payment`), each importing only what that section needs (e.g. `payment.js` skips Bootstrap JS/CSS entirely). All `resources/css/*.css` files import `base.css` for shared design tokens/utilities. When adding a page, `@vite([...])` the correct section entry in its layout rather than pulling in another section's bundle.

**Never write a Blade directive name inside a CSS or JS comment in a `.blade.php` file — escape it as `@@vite` / `@@stack(...)`.** Blade doesn't parse CSS; it compiles every `@directive` it finds anywhere in the file, comment or not. A bare `@vite` mentioned in prose inside `@push('styles')` compiles to `app('Illuminate\Foundation\Vite')()` with zero arguments and 500s the page with `ArgumentCountError` — that was `/admin/prescriptive`, `/admin/users` and `/admin/properties/{id}` simultaneously (v7.5). `Blade::compileString()` will not catch it, because the compiled output is valid PHP; only a real render will. The sweep command is in `project.md` v7.5.

## Testing

`tests/` has the default Laravel skeleton (`ExampleTest.php` in both `Unit` and `Feature`) plus `tests/Feature/RateLimitingTest.php` — there is no real test suite covering booking/pricing/payment logic yet. The migrations use MySQL-only syntax and don't run on the SQLite test DB, so tests that need tables create minimal ones themselves (see `RateLimitingTest::makeUsersTable()`); `Feature\ExampleTest` fails for that reason. Testing config uses in-memory SQLite, array session/cache/mail, sync queue (see `phpunit.xml`).

## Deployment

Production runs on Render (Docker, free tier, no persistent disk, blocks outbound SMTP entirely) against an Aiven MySQL database, with Cloudinary for images, Pusher for realtime, and Brevo's HTTPS API (not SMTP) for mail via a custom `Mail::extend('brevo', ...)` in `AppServiceProvider`. `docker/start.sh` branches on `APP_ENV` (`local` skips config/route/view caching for live-reload; anything else caches them) and only runs migrations when `RUN_MIGRATIONS=true` is set for that deploy. A scheduled task (`bookings:auto-checkinout`, registered `everyMinute()` in `routes/console.php`) runs via an external cron pinger hitting the token-gated `GET /cron/run-schedule/{CRON_SECRET}` route, since Render Cron Jobs aren't free — that route just calls `Artisan::call('schedule:run')`. Locally, `composer dev` runs `php artisan schedule:work` alongside the other dev processes so this (including the stale-pending-booking auto-cancel) actually fires while developing; without it, nothing invokes the scheduler and pending bookings never get swept. Full details, required env vars, and the Aiven CA-cert/TLS setup are in `project.md` §15 — read it before changing deployment-related code (Dockerfile, `docker/start.sh`, `render.yaml`, `config/database.php`'s `aiven` connection).
